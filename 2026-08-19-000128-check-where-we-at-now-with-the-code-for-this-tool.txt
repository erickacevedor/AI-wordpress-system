  What the tool is

  A site-agnostic Elementor page factory. You point it at a WordPress site's
  exported Elementor kit; it mines that site's real design system, then
  generates import-ready page JSON in that brand. Zero dependencies — plain
  Python 3, so it runs under any agent or CI.

  The architecture is a deliberate two-layer split (documented in AGENTS.md, the
  canonical guide; CLAUDE.md/GEMINI.md/.cursor/rules are thin stubs pointing at
  it):

  - Portable layer — never changes site to site: scripts/elementor_builder.py
    (350 lines), scripts/validate-page.py, scripts/responsive-audit.py, plus two
    portable skills (elementor-kit-onboarding, full-output-enforcement).
  - Per-site layer — generated once per website: projects/<site>/tokens.json
    (brand), KIT-ANALYSIS.md (the why), and five generated <site>-* skills.

  How it works

  kit export → onboard (mine palette/fonts/button/voice) → tokens.json +
  <site>-* skills
                                                                ↓
                pages/<slug>/build.py  ──imports──> scripts/elementor_builder.py
                                       ──reads────> ../../tokens.json
                                                                ↓
                                                    <slug>.json  (single-page
  wrapper)
                                                                ↓
                                scripts/validate-page.py  ← REQUIRED GATE, must
  exit 0
                                                                ↓
                                Elementor import (or, for Lenz, headless via wp
  eval-file)

  The clever bit is correctness by construction. elementor_builder.py bakes the
  structural and responsive standards into the helpers themselves — section()
  always emits full-width band → one boxed 1140px container; grid() always sets
  tablet/mobile column counts; column(width=…) always forces 100% on mobile;
  headings auto-get mobile sizes. So a page built entirely through the library
  passes the validator by default. Brand values are never hardcoded there —
  they're injected from tokens.json, which is what keeps the library reusable.

  validate-page.py is the objective "done" gate: JSON parses, wrapper shape,
  unique element ids, exactly one H1 (inverted for header/footer parts — those
  must not have one), no display_condition_list gates, no dead/localhost links,
  and it delegates the full responsive sweep to responsive-audit.py.

  Two escape hatches for designs Elementor can't express natively: gradient_bg()
  (real, still editable in the UI) and classes="…" (CSS Classes field → site
  stylesheet). Rule of thumb in the docstring: emit native if possible, reach
  for a class rather than approximating.

  What's genuinely well-designed

  The load-bearing insight is "globals are usually fake." site-settings.json
  frequently still holds Hello Elementor defaults (#6EC1E4, Noto Sans Coptic),
  so onboarding mines the actual inline widget styling instead — rank hex
  frequency across content/page + templates, assign roles by position (header bg
  = brand dark, button bg = CTA, frequent light tints = alternating bands).
  Everything downstream that works, works because of this. A system that trusted
  the globals would produce confidently off-brand pages on most real kits.

  Knowledge is sorted into three tiers by kind, and each fact lives in exactly 
  one. Machine values → tokens.json. Judgment that needs prose → SKILL.md.
  Invariants that must never vary → elementor_builder.py. That's why brand.py
  starts with "no brand constants are typed twice" and reads everything from
  tokens. It's the discipline most agent-tooling repos don't hold.

  Two gates, correctly placed. One before any page exists (verify the generated
  skills against the live site — "fix the skills, not the output") and one
  before handoff (validate-page.py, exit 0 or it's a blocker). Catching brand
  errors at the skill level means you fix them once instead of in every page
  forever.

  The design read is a real agent-control mechanism. Forcing a one-line
  declaration — "a new AC Installation page, sibling of AC Repair — gradient 
  hero with H1 + sub-line + red CTA, white intro row with photo + floating '40+'
  badge…" — before generating gives the human a cheap veto at the point where
  correction is nearly free. And "if the brief genuinely diverges, ask one
  question. Otherwise declare and proceed" is the right calibration; it doesn't
  turn into an interview.

  The page-audit "do NOT fix" list is a subtle, smart touch: it names
  intentional brand choices so generic web-redesign instincts don't fight the
  kit. Square corners on gcreliable aren't a mistake to be rounded.

  Tier 1 — Close the build → live loop

  1. Promote the headless importer to the portable layer. This is the
  highest-leverage thing available, and it's nearly free:
  projects/lenz/tools/import-page.php is already 100% site-agnostic — I grepped

  import-template.php is too, apart from a fallback slug prefix.

  Right now every site except Lenz ends at "hand the user a JSON and describe
  where to click." That means the system's output is never mechanically
  confirmed to render. Moving these to scripts/import-page.php +
  scripts/import-template.php (and generalizing set-globals.php to read any
  tokens.json) gives every site an idempotent, re-runnable deploy:

  build.py → validate-page.py → import-page.php → live page, verified

  It also converts the two traps Lenz documented — wp_slash() on
  _elementor_data, and include/general display conditions on theme parts — from
  tribal knowledge into code that every site inherits. Effort: an hour. Do this
  one first.

  2. Verify the render, not just the JSON. Once import is scriptable, add
  scripts/verify-render.py: fetch the URL, assert HTTP 200, count e-con
  containers against the JSON's container count, and flag any that Elementor
  dropped. Lenz already does this by hand (grep -c 'e-con', expect ~320). This
  catches the entire class of failure the validator structurally cannot — where
  valid JSON imports and renders wrong. A screenshot step on top would close the
  visual gap that PREVIEW.html only approximates.

  Tier 2 — Make onboarding deterministic

  3. scripts/analyze-kit.py — mine the kit mechanically. Onboarding is the step
  every page's quality descends from, and it's currently the least reproducible:
  an agent greps hex codes and eyeballs frequency. That work is deterministic —
  rank hex colors across content/ + templates/, rank font_family, bucket
  heading font_size, extract a representative button, dump the
  section-background sequence, count widget types.

  Have a script produce that as JSON, and the agent's job becomes judgment
  (which color is the CTA, is this palette real or Hello-Elementor default)
  rather than extraction. Faster, repeatable, and it removes the failure mode
  where two onboardings of the same kit disagree. This is also what would let
  you re-onboard a site cheaply when the client's kit changes — which already
  happened once (a4394e7 Refresh the Dolan kit export).

  used, only 7 shared by all of them. Color roles diverge hard —

  dolan       blue, white, black, accent, text

  petitt      primary, secondary, accent, text, white, soft_gray, blue_2, red_2,
  text_2

  shared base, and why no tool can consume tokens across sites. A required core

  scripts/validate-tokens.py, unlocks everything in Tier 3. Migrating five sites
